# Task 4.2, second slice — the shell-free Git runner

Date: 2026-09-14
Change: `go-owned-headless-core` (P4, task 4.2)

## What landed

`networking/internal/gitcheckout` now owns the invocation half of the checkout
layer, ported from `electron/main/managed/git/process.ts` and `command.ts`:

- `version.go` — the version rules: three plain components with no leading zero,
  a distro suffix only when a space, a dot or a dash introduces it, ordering that
  ignores that suffix, and the policy that turns an out-of-range version into
  `git.version_unsupported` with both numbers in the message.
- `runner.go` — `PinExecutable`, `AssertExecutable`, `RegisterExecutable` and the
  `Runner`: a direct, shell-free spawn with the deterministic prefix
  (`--no-pager`, no credential helper, no hooks, and git's long-path APIs on
  Windows), the closed environment, one shared output budget across both streams,
  the timeout and the cancellation, the exit code or the signal that ended it, and
  redaction of everything that leaves the package.
- `platform_unix.go` / `platform_windows.go` — the file identity and the exit
  status, the only two things that differ per platform.

## Two decisions worth recording

1. **The Windows fingerprint is the same two numbers Node reports.** Windows has
   no inode, so the device is the volume serial number and the inode is the file
   index, read through `GetFileInformationByHandle` — which is exactly what
   libuv fills `stat().dev` and `stat().ino` with. It would have been tempting to
   pin size and modification time only, but then the core could not verify a
   fingerprint the shell had written, and the switch would have had to happen on
   one platform at a time.
2. **Output is redacted where it is observed, not where it is printed.** A
   command's arguments, stdout and stderr all pass through `RedactOutput` before
   they are assembled into a `Result`, so no caller can forget: a URL's
   credentials, an `Authorization` header and the `token=`/`password=` labels are
   removed even if a future caller logs the whole result.

## Evidence

`runner_test.go`, `version_test.go`, `env_test.go`:

- the version table (what git prints, including `2.43.0.windows.1` and an Apple
  Git suffix; and what must be refused) plus comparison, policy and the
  record's own consistency;
- a real pin on a real file: the fingerprint, an unchanged re-check, a rewritten
  file (`git.executable_changed`), a deleted file
  (`git.executable_unavailable`), a directory and — on POSIX — a file without an
  executable bit;
- the machine's own git through the runner: a version probe, a command that exits
  zero with its bounded observation, a command that fails
  (`RequireSuccess` → `git.command_failed`), and the deterministic prefix with and
  without the Windows arguments;
- the four ways a command ends badly, each with a POSIX script the runner
  executes directly: a timeout, a cancellation, an output limit — and a command
  that prints a credential URL and a token, which come back redacted;
- `gofmt`, `go build`, `go vet` and the package tests, plus `go vet` for
  `GOOS=windows` and `GOOS=linux`.

## The Windows leg, and one test of mine it corrected

The whole Go suite was run on the Windows machine (`.run/windows/go-suite-windows.txt`):
`go build`, `go vet` and `go test ./internal/... ./cmd/...` all exit 0, with
`internal/gitcheckout` green in 2.8s. That is the only place the Windows half of
this slice actually executes — the volume serial number and file index read
through `GetFileInformationByHandle`, the file index split across two 32-bit
halves, and the runner starting a real git without a shell.

It also corrected a test. `TestParsePinsTheFingerprintTimeContract` edits the
interop golden, and the golden spells its paths the way the shell wrote them, on
posix: Windows refuses the document for that reason alone, whatever the two
numbers say. The test now carries the same platform guard as
`TestGoldenBytesRoundTrip`, with the reason written next to it. The contract it
pins is platform-independent, and the shell asserts its half of it on every
platform.

## Two races the first CI run found

The first Linux run failed `TestRunnerBoundsAndRedacts` with an empty stdout, and
it was right to. Both problems were in the runner, not in the test.

1. **Draining pipes by hand races with `Wait`.** The runner read
   `StdoutPipe`/`StderrPipe` itself and only then waited. `Cmd.Wait` closes those
   pipes when the process ends, so a read that had not happened yet lost its
   bytes: on a fast machine the window is invisible, on a loaded two-core runner
   it is not. The two streams are now `boundedWrite` destinations that the
   `exec` package copies into, which makes `Wait` mean "every byte written was
   read".
2. **Killing the process is not enough to end the invocation.** A command that
   spawned a child — a shell running `sleep`, or a git starting a helper —
   leaves that child holding the output pipe, and `Wait` then blocks on a pipe a
   stranger still holds. The test caught it as a 30-second timeout where the
   timeout was 150 ms. On POSIX the command now starts in its own process group
   and the group is what gets killed; on Windows the process is killed, which is
   what that platform offers from here.

The second one matters beyond the test: a git that hangs is exactly the case the
timeout exists for, and a timeout that returns thirty seconds late is not one.
