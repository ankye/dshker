# Core refusal codes survive the private channel

The shell's private-channel frame decoder rejected any error code outside `p2p.*`, while the core answers with the whole typed vocabulary declared in `networking/internal/protocol/refusal.go`: `p2p.`, `managed.`, `launcher.`, `runtime.`, `remote.`. A refusal such as `runtime.port_in_use` (a launch blocked by an occupied port) therefore failed frame admission, closed the entire channel, and surfaced to the user as a bare `p2p.protocol_mismatch` — after which every core operation failed with `p2p.helper_unavailable` until the app restarted. The real cause was unreachable from every surface, and the shell's own `ipc-error-codes.ts` mapping (which expects `runtime.port_in_use` and friends) could never run.

`peerErrorCode` in `electron/main/p2p/wire.ts` now admits exactly the families the core's `protocol.RefusalFamilies` declares, with the same 96-byte cap and `[a-z_.]` suffix rule. The widened check also repairs the reverse direction in `PeerRpc.#handle`, which previously rewrote any non-`p2p.` handler failure to `p2p.operation_failed` before replying to the core.

Verification on 2026-09-14: with port 31888 held by an orphaned DSH Web child, a launch reported `runtime.port_in_use` in the launcher console, the channel stayed alive, and a second launch in the same session succeeded once the orphan was stopped (button flipped to 终止进程, port owned by the new core-supervised child). `electron/main/p2p` suite: 383 passed; the one failure (`selection-preferences.test.ts` owner-permission bits) reproduces without this change on Windows and is unrelated. `vue-tsc` clean.

Two operational findings from the same investigation, recorded here because they will recur: `build/p2p/*/dshkerd*` binaries must be rebuilt after any `networking/` change (`node tools/build-peer-helper.mjs --platform <p> --arch <a>`) — a stale binary that predates the `--catalog` argument exits with `p2p.invalid_arguments` before printing anything, which reads as `p2p.helper_parent_unavailable`; and force-killing the launcher orphans the core's DSH Web child, which then holds the launch port.

Follow-up on 2026-09-15 (commit d462b30): the stale-pair wedge itself is fixed in `recordMembers`. When both machines re-enroll, each side's catalog held the other's old identity as an active pair; the member sync's rewrite dropped it, `AssertTransition` refused with `p2p.revocation_required`, and the sync wedged permanently — Windows could see the Mac while the Mac saw only itself, and neither the tab nor the member list converged. A row of the rewritten service that the coordinator's list no longer carries is now carried forward as `pairState: "revoked"` instead of vanishing, which the guard admits (active → revoked), keeps the loss visible on screen, and lets the row disappear on the following rewrite. The Windows side had been unblocked by hand the same way before the fix existed; the Mac healed through the same rule once it ran the fixed build.
